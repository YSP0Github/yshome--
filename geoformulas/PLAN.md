> 站名：**地球物理公式大全**（目录/仓库名沿用 `geoformulas`）
> 版本 v0.2　2026-10-10

---

## ⚠ 实现状态（v0.2 更新，以此为准）

调研结论与内容组织思路仍然有效，但**技术选型已按用户决策调整**，下面第 5 节的 Astro 方案已被替换：

| 原方案 | 实际采用 | 原因 |
|---|---|---|
| Astro 5 + React islands | **零打包：TypeScript 直出原生 ES 模块 + KaTeX 全局引入** | 用户要求「怎么方便怎么来、能纯前端最好」；且本环境 esbuild 原生二进制无法启动，Vite 不可用 |
| 内容存 YAML + Zod | **内容存 TS 模块，一条公式一个文件** | 编译期类型校验比运行时 schema 更早发现问题；函数可直接内联在卡片里（可视化的 compute 就是普通函数） |
| 单套学科树 | **4 套分类体系（学科 / 数学工具 / 方法 / 物理量）+ 读者层级 + 完成度** | 用户要求「可据此排序检索、做气泡图与系谱图」 |
| 仅列表 + 图谱 | **首页 / 多维浏览 / 详情页 / 气泡图 / 系谱图（全局 DAG + 单条血缘）** | 同上 |

当前实现细节见 **`README.md`**。已落地：19 条公式、116 步推导、20 个交互可视化、26 条依赖边，`npm run check` 全绿。

## 0. 一句话定位

> **把地球物理学的公式从「排版文本」升级为「结构化数据」，并由此自动生成可推导、可交互、可联动、可溯源的知识页面。**

不是公式速查表，也不是第二本教科书。核心目标是：让用户能在浏览器里**看懂每一步怎么来的**、**拖动滑块看符号如何驱动物理**、**沿着依赖图谱走通一条逻辑链**。

## 1. 为什么要这样做（调研结论的直接推论）

调研了 GitHub + 全网约 30 个候选项目后（详见 `docs/references.md`），结论是：

| 现有生态 | 强项 | 缺口 |
|---|---|---|
| geoscixyz 系列（gpg / em / geosci-labs） | 知识结构权威完整、CC-BY 授权 | 依赖 Binder 起内核，慢；无中文；无逐步推导；公式间无依赖 |
| SEG tutorials / UW ESS412 / EPS164 | 公式 + 代码 + 练习三位一体 | 是 Notebook 不是网站，读者要会 Python |
| PhysicsHub / Explorable Physics | Web 交互与排版成熟 | 只做通识物理，完全不覆盖地物 |
| HBCSE Interactive Derivations | 唯一有「交互式推导」 | 只 5 个样例，没体系 |
| Pyodide 系 / Three.js 系 demo | 证明浏览器能跑数值与三维 | 分散的单点 demo |

**三者交叉处是空白：×地球物理 ×逐步推导 ×全站式。**
同时技术风险已被前人趟平（KaTeX / Plotly / Pyodide / Three.js 在浏览器端全部成熟），所以本项目的成败取决于 **内容工程方法**，而不是能不能做出来。

## 2. 三个必须做成的差异化点

1. **符号级联动（Symbol Linking）**
   公式里每个符号都可 hover/点击：高亮符号表中对应行、点亮图中对应曲线、显示量纲与典型取值。这是「公式变成数据」后自动获得的红利，也是教科书和现有网页都做不到的。
2. **推导即变换（Derivation as Transformation）**
   每一步推导显式标注「用了什么变换/代入/近似」，并给该步做上色：`代入`、`消去`、`线性化`、`坐标变换`、`忽略高阶项`。读者可单步展开、可跳到该步依赖的更早公式。
3. **依赖图谱（Formula Graph）**
   每条公式声明上游（由谁导出）与下游（导出谁），自动生成有向图。例如：`Navier 方程 → P/S 波速 → Snell 定律 → 射线参数 → 走时双曲方程 → NMO 校正 → 叠加`。这条链就是网站的主导航。

**目标规模**：核心公式 **约 600 条**（每条都带完整推导），其中「中国学生常考/常用」条目优先。MVP 阶段先做透 `02 体波与射线理论`（约 40 条），把工程链路跑通。

**每条公式的完成度等级**（避免完美主义陷阱）：

| 等级 | 要求 | 适用 |
|---|---|---|
| L1 | 公式 + 符号表 + 一句话物理意义 + 来源 | 冷门/边缘公式 |
| L2 | + 完整分步推导 + 静态 SVG 配图 | 大多数公式（**默认标准**） |
| L3 | + 交互式可视化（滑块驱动的图形） | 核心公式，约占 30% |
| L4 | + 数值仿真/动画/三维 + 可运行代码 + 数值算例 | 王牌公式，约 50–80 条 |

## 4. 核心：公式的数据结构

**这是整个项目最重要的一次设计。** 所有页面、图谱、搜索、质量检查都从这个 schema 派生。

```
FormulaCard
├── meta        id / 中文名 / 英文名 / 别名 / 版本 / 作者 / 更新日期
├── domain      一级学科 · 二级专题 · 关键词[]
├── statement   主公式 LaTeX · 常见变体 LaTeX[]
├── symbols[]   符号 · 名称 · 量纲 · SI 单位 · 典型取值 · 是否为复数/张量
├── conditions  适用前提[] · 隐含假设[] · 失效边界
├── derivation[]  Step{ 编号 · LaTeX · 说明 · 操作类型 · 引用资源 }
├── viz[]        Visualization{ 类型 · 绑定的数值函数 id · 默认参数 · 滑块定义 }
├── numerics     数值实现函数名 · 精度/稳定域说明 · 参考实现路径
├── links        upstream[] · downstream[] · seealso[]
├── refs         教科书章节 / 论文 DOI / 在线资源
└── difficulty   建议前置知识标签[]
```

配套文件：

- `schema/formula.schema.yaml` —— 用 Zod 生成 TS 类型 + 运行时校验
- `examples/normal-moveout.yaml` —— 样板条目（见下节）
- `scripts/new-formula.mjs` —— CLI 生成骨架，强制填写必填字段

> 设计原则：**公式本体必须与页面表现彻底解耦**。同一份 YAML 可以渲染成网页、图谱节点、Markdown 卡片、Anki 复习卡、PDF —— 这是长期复利。

## 5. 技术架构（推荐方案）

### 5.1 选型

| 层 | 选择 | 理由 |
|---|---|---|
| 框架 | **Astro 5 + React islands** | 数千条内容页需要静态生成；只有交互小部件需要 hydrate，首屏极快；Content Collections + Zod 天然支撑 schema 校验。**优于 Next.js**：本项目的重心是内容站而非 Web App |
| 数学排版 | **KaTeX**（SSR 预渲染） | 比 MathJax 快一个量级，Astro 里可构建期渲染成 HTML，不阻塞首屏 |
| 二维图表 | **Plotly.js**（科学图）+ **Observable Plot**（轻量）+ **Mafs**（React 数学几何图形） | 按复杂度选用，避免一刀切 |
| 场 / 网格渲染 | Canvas 2D / WebGL（regl） | 波场快照、位场热图 |
| 三维 | Three.js（懒加载） | 地球模型、磁力线、三维射线 |
| 依赖图谱 | Cytoscape.js 或自绘力导向 SVG | 节点 600 个级别足够 |
| 搜索 | **Pagefind**（静态索引，支持中文分词）+ MiniSearch 做符号/变量搜索 | 纯静态，无需后端 |
| 数值内核 | **纯 TypeScript 函数** 为主 + **Pyodide**（懒加载）兜底 | TS 覆盖 80% 公式（实时、可测、无加载成本）；需要 NumPy/SciPy 的重仿真才走 Pyodide |
| 样式 | Tailwind CSS + 自定 `(light)` 主题变量 | 保证浅色/深色一致性 |
| 部署 | GitHub Pages（免费静态站）/ Cloudflare Pages | 无后端成本 |

### 5.2 目录结构

```
geoformulas/
├── src/
│   ├── content/formulas/        # 按学科分目录的 .yaml/.mdx（内容主体）
│   ├── components/
│   │   ├── Formula/             # 主公式与符号表（hover 联动）
│   │   ├── Derivation/          # 分步推导组件（单步展开/高亮）
│   │   ├── viz/                 # VizPlot VizField VizScene VizSliders VizPyodide
│   │   └── Graph/               # 依赖图谱
│   ├── numerics/                # 纯 TS 数值实现，一个公式一个文件，配 vitest 单测
│   ├── layouts/FormulaPage.astro
│   └── pages/                   # 首页 / 图谱页 / 学科页 / [id].astro / 搜索
├── schema/formula.schema.yaml
├── scripts/                     # CLI 脚手架 · CI 校验 · 图谱导出
├── docs/references.md
└── examples/
```

### 5.3 单页信息布局（固定模板，保证全局一致性）

```
[面包屑 + 图谱定位]
主公式（大号 KaTeX）          ┌ 编号 · 难度 · 学科标签
适用条件 / 假设（警告条）      │ L1-L4 完成度徽标
─────────────────────────────
① 符号表       （hover 联动高亮公式与图形）
② 物理意义     （3–5 句话说清「它回答了什么问题」）
③ 分步推导     （可单步展开；标注每步的变换类型；链接到依赖公式）
④ 可视化       （滑块 + 图形；图形与符号双向联动）
⑤ 数值算例     （一组真实数量级的输入 → 输出，可复制）
⑥ 最小实现     （15–40 行 Python/TS 代码，可直接跑）
⑦ 依赖网络     （上游 3 条 / 下游 3 条，可点击跳转）
⑧ 参考来源     （教材章节 · DOI · 链接）
```

## 6. 可视化分级标准（统一组件，避免各页各做一套）

| 级别 | 实现 | 典型例子 |
|---|---|---|
| **V0** 几何示意 | 手写 SVG + KaTeX 标注 | 层状介质射线路径、断层几何、偶极子磁力线 |
| **V1** 参数曲线 | Plotly.js / Observable Plot + 滑块 | NMO 走时曲线 vs 偏移距、AVO 曲线 vs 入射角、磁异常曲线 vs 距离 |
| **V2** 场渲染 | Canvas heatmap + 等值线 / 箭头场 | 重力异常场、位移梯度场、电磁波扩散、温度场 |
| **V3** 数值动画 | requestAnimationFrame + 有限差分 | 声波 FD 波场传播、标量波动方程动画、Smylie 型演示 |
| **V4** 三维 | Three.js 懒加载 | PREM 剖切、三维射线追踪、磁场空间结构 |
| **V5** 重内核 | Pyodide 懒加载（首次 ~10MB） | FWI、CPU 密集反演、需要 SciPy 的方程求解 |

> 规则：**能用低级别就别上高级别**。V5 全站最多 10 个，且必须异步 + 骨架屏 + 缓存 worker。

## 7. 内容生产流水线（决定产能的关键）

```
① 选题  ← 学科树的 breadth-first 遍历，每个专题一次选 5–10 条
② 起草  ← AI 生成初稿（公式 LaTeX + 符号表 + 分步推导 + 算例）
③ 校验  ← 三道自动关卡（CI 强制）：
          ├─ Schema 校验（Zod）
          ├─ 编译校验（KaTeX 必须能渲染；符号必须在 symbols[] 中声明，否则报错）
          └─ 数值校验（TS 实现 vs SimPEG/obspy/解析特例交叉对比，误差阈值）
④ 人会审 ← 只看 AI 容易错的地方：假设条件、符号约定（不同教材符号冲突！）、量纲
⑤ 配可视化 ← 从 V0–V5 里选最低够用级别
⑥ 发布
```

**符号约定冲突是最大隐蔽坑**（如 Lamé 常数 λ/μ、泊松比 vs 慢度 ρ vs 密度 ρ）。必须用一张全局 `SYMBOLS.md` 锁定约定，并在 ADR 里记录例外。

## 8. 分阶段路线图

| 阶段 | 目标 | 产出 | 预估 |
|---|---|---|---|

## 9. 质量与工程规范

- 每条公式有稳定 slug / 永久 URL，支持 `?step=3` 深链到某一步推导（参考 Gravity 的 43 步导览设计）
- 中英双语：术语表统一管理 (`terms.yaml`)，页面可切换
- CI 必须跑：schema 校验、KaTeX 渲染、链接检查、依赖边闭环检查、符号未声明检查、数值回归测试
- 每条 L3/L4 公式的数值函数必须配单测（对解析解或已知结果回归）
- 移动端适配：>= 375px 宽度时公式与图表不溢出（这在公式站是最常见的失败点）
- 无障碍：所有可视化必须提供等价的文字描述或数据表

## 10. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 内容做不完，半途而废 | **高** | 严格按 L1–L4 分级，先全树铺 L1，再逐级加深；绝不追求每条都完美 |
| 符号/单位约定打架 | **高** | 全局 `SYMBOLS.md` + 校验脚本，第二条冲突条目就会在 CI 报错 |
| 公式推导错误传播 | 中 | 数值交叉验证 + 每条公式标注来源章节 + 开放 issue 纠错 |
| 版权风险 | 中 | 只借鉴结构与口径，文字和图示原创；每页标注参考来源；不搬运 SEG / 商业教材原文 |
| 可视化逐个手搓，成本失控 | **高** | V0–V5 分级 + 统一组件 + 参数化配置，禁止每页写 custom 图表代码 |
| Pyodide 首屏加载慢 | 中 | 只在 L4/L5 懒加载；所有 V0–V3 必须纯 JS |

## 11. 需要你拍板的 5 个决策点

1. **主线取舍**：先做「地震学为主」（你工作区里有 SPECFEM3D 和大量 mseed，看起来是地震学方向），还是「全学科均摊」？建议**前者**，把 P1 的学科换成最贴合你研究的那条。
2. **语言**：只做中文 / 中文为主英文术语 / 中英双语并行。建议**中文正文 + 英文术语保留**，成本低收益高。
3. **代码栈偏好**：是否可以接受 Astro（推荐）？还是希望沿用你熟悉的 React/Vue 技术栈？
4. **可视化深度上限**：是否要投入 V4（Three.js 三维）和 V5（Pyodide）？这两级会让工期增加约 40%，但也是最有传播力的部分。
5. **更新方式**：本地 Vite/Astro 开发（推荐，迭代快）还是需要把内容沉淀成 YSKY/腾讯文档之类的在线知识库协作？
